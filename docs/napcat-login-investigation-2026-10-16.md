# NapCat Windows 周期性登录失效排查（2026-10-16）

时间均为 Asia/Shanghai。本轮只读检查运行环境、日志、配置、数据库任务时间及上游源码，新增本记录；未重启服务、修改运行配置、尝试 QQ 登录或更换客户端。

## 结论与边界

已确认故障发生在 QQ 登录会话层：QQ 内核发送 `KickedOffLine`，说明“你的账号当前登录已失效，请重新登录”；NapCat 随后主动重建 Worker，自动快速登录被拒绝，提示“你的用户身份已失效，为保证账号安全，请你重新登录”。因此 WebUI 回到 QQ 登录流程，OneBot 断开后无法靠 WebSocket 重连恢复。

优先怀疑当前账号/设备/客户端环境被 QQ 的会话校验或风控拒绝。日志没有提供更细的服务端原因，也没有明确的“其他设备登录”或“检测到第三方工具”提示，不能把具体风控触发项、账号被封或某个版本缺陷当作已证实结论。

本轮在 `artifacts/feasibility/napcat.stdout.log` 找到了持续保留的控制台日志，补足了此前 `docs/incident-2026-10-16-disconnect.md` 未获得的下线证据。虽然 NapCat 的 `fileLog=false`，这份 stdout 重定向日志确实存在。

## 本机状态

- NapCat：`4.18.37`；实际 QQ：`9.9.33-52230`（以 QQ 自己的 `resources/app/package.json` 和启动日志为准）。
- 项目 QQ 主进程 PID `35164` 从 10 月 15 日 22:05:59 持续运行；当前 Node Worker PID `31204` 创建于 10 月 16 日 21:33:48，符合失效后重建 Worker 的时间线。
- Python 服务 PID `9712` 从 10 月 16 日 00:56:03 持续运行，监听 `127.0.0.1:8080`，`bot.stderr.log` 为空。Python 虚拟环境启动器及其解释器进程属于同一次启动。
- WebUI 监听 `6099`；22:10:32 只读状态查询为 `isLogin=true, isOffline=false, loginPhase=ready, coreReady=true`。机器人 22:01:07 已重新连上。
- 反向 WS：`ws://127.0.0.1:8080/onebot/v11/ws`；心跳和重连均为 30 秒。
- WebUI 已设置 `autoLoginAccount`；最近多次失效后的快速登录均被 QQ 拒绝，单纯再配置自动登录不能解决本例。
- 全局 `config/napcat.json` 与账号 `config/napcat_3653125828.json` 的 `bypass.hook/window/module/process/container/js` 均为 `false`；`o3HookMode=1`。后者是独立配置项，不能据此认为上述反检测已启用。
- 账号配置启用 `autoTimeSync`，最近几次同步偏差不足一秒，不支持明显时钟错误的解释。
- 本机还有日常 QQ 的独立主进程，安装路径不同；没有证据证明两者登录同一个账号。项目账号数据日志指向 `D:/SysFolders/Documents/Tencent Files/NapCat/data`，不能仅凭二者共有 Electron `user-data-dir` 就断言登录数据冲突。

## 建议处理顺序

### 1. 先核实账号与单实例条件

在手机 QQ 查看“设置 → 账号安全”及登录设备，处理实际出现的安全验证；确认机器人账号没有同时登录另一台 PC、另一套 NapCat 或日常 QQ。保留正常的手机登录。这里核对的是同一账号，不需要关闭使用其他账号的日常 QQ。

当前已恢复在线，无需为了诊断反复扫码或强制重启。身份已失效时，快速登录不能代替 QQ 要求的新授权。

### 2. 优先做反检测配置的单项对照

当前所有反检测项都关闭，这是具体可检查的配置因素，但尚未证明它就是失效原因。

1. 安排可以中断机器人连接的时间，备份当前 NapCat 的 `config/napcat.json` 和账号配置。
2. WebUI 打开“配置 → 反检测”，先仅将 `Hook` 从关闭改为开启，保存；其他项及 `o3HookMode` 保持现状，避免混入多个变量。
3. 只重启本项目的 NapCat 并按需完成授权。该开关在原生模块初始化时读取，保存不代表已对当前 Worker 生效。
4. 在同一网络、同一 QQ/NapCat 版本下观察至少 8 小时，记录有无新的 `KickedOffLine`。如果出现启动或收发异常，恢复备份并重启项目 NapCat。
5. 若仍复发，保留结果；再逐项评估 `Module`、`Process`、`JS` 等当前版本提供的选项。不要把六项全部开启视为必然有效的修复；Windows 本机也不能直接套用 Docker 的 Container 配置经验。

以上是有源码依据的配置试验，不是已验证修复，也不能保证撤销 QQ 对既有身份的拒绝。不要用定时重启、频繁自动登录或伪造在线状态替代有效登录。

### 3. 用基线对照区分账号/环境与接入端

如果单项试验仍失败，在维护窗口分阶段测试，每次只登录一个 PC 实例：

| 对照 | 条件 | 结果说明 |
| --- | --- | --- |
| 官方 QQ 基线 | 同一账号、同一电脑和网络，仅官方 QQ，无 NapCat 注入，观察至少 8 小时 | 仍退出则优先处理账号安全、登录设备或网络环境；暂时稳定只能说明基线通过 |
| NapCat 空闲基线 | 官方基线稳定后，运行 NapCat，暂停 OneBot 连接，观察至少 8 小时 | 仍失效则问题可在 QQ/NapCat 环境独立复现 |
| 完整接入 | 基线稳定后恢复原反向 WS 和业务，继续观察，目标至少 24 小时 | 若只在接入业务时复发，再根据实际调用和发送行为做进一步收敛 |

测试保持网络出口稳定；若使用 VPN/TUN，先检查 QQ 的实际路由，只有确认出口变化时才做固定出口对照。当前没有证据将代理、休眠、DNS 或某个公网 IP 定为原因。

### 4. 版本更新与替代运行环境作为后续措施

截至本轮核查，上游最新发布为 `4.18.38`，本机为 `4.18.37`。新版本说明列出发布流程、macOS GUID、Linux 路径、合并转发表情等变更，没有承诺修复本例 Windows 周期性登录失效。可以在备份后单独更新 NapCat 做对照，但不能称为确定修复。

不要照抄 Linux issue 中的 QQ `3.2.22` 降级建议到 Windows，也不要同时更换 QQ、NapCat、设备标识与网络。若需要更换 QQ 构建，先核实目标构建与 NapCat 的兼容性，保留旧安装和回退路径。

若 Windows Shell 空闲基线仍持续失败，可再评估上游提及的 SnowLuma，或在独立 Linux 环境复测。部署迁移也是对照方案，不能保证消除服务端账号风控。本项目业务继续通过 OneBot v11 接入的可行性需按目标接入端实际能力验证。

## WebUI 管理登录与 QQ 登录的区别

本机 `napcat.mjs:49135–49177` 对 WebUI 管理凭据设置一小时有效期；Worker 重建还会更换进程内签名密钥。单独回到 Token 登录页时，应先查 QQ/OneBot 状态：若 QQ 仍在线，只需重新进入管理页。本例另有明确的 QQ `KickedOffLine`，不能只按管理凭据过期处理。

同一文件 `82545–82546` 将 `ErrType=1, ErrCode=3` 处理为二维码过期并重新取码。这些每约两分钟出现的后续日志，不是周期性踢下线的根因。
